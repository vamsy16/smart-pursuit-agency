01 · Architecture

Public method.
Sealed memory.

The entire runtime fits in one sentence: an agent reads contract-shaped files, produces contract-shaped files, and a CI check refuses any output that violates them. No service holds state, because state in a service is state you cannot clone, grep, encrypt or hand to a successor.

CLIENT / BROWSERGitHub Pages (public repo, free, HTTPS, CDN). Receives the weekly report as one self-contained HTML file. Never authenticates, never logs in, never installs anything.site workflow ready
FOUNDERApproves via a git branch and a pull request on a phone. Owns every decision involving money, promises, scope or relationship repair (autonomy level L0 by constitutional rule).design final
AGENT RUNTIMEArena agent in a sandbox with the repo checked out. Nine roles, one kernel, eight rituals. The only compute; the only throughput ceiling.active
os/ · design/ · site/Constitution, kernel, engines, playbooks, templates, sessions, stack, memory and the published site. Read by the agent on every session boot; the file set is the programme.live

GITHUB ISSUESTicket queue and the approval surface. One PR per client per week; merged means shipped. A tech-literate client may be given a read-only private repo of their own.optional
# the whole runtime, expressed as a loop
for ritual in ["morning", "intake", "produce", "report",
               "prep", "log", "ingest", "money", "retro"]:
    open vault(slugs)                       # decrypt → .vault-work/
    state  = read("SOVEREIGN", "AGENTS", "STATEBOARD", playbook)
    skill  = load("os/playbooks/PB-NN-*.md")   # rule A11: a request maps to a
                                           # skill; no skill ⇒ write it, then run it
    out    = roles.execute(ritual, state, skill)  # 9 roles, file-to-file handoff
    score  = gate(out)                      # 100 pt rubric, hard fails
    if score < 90: out = critique(out); continue
    branch, commit, open_pr(out)            # nothing client-facing is sent
    seal vault(slugs)                        # gzip → encrypt → stage .age
    append("memory/log/<date>.md", one_line)
    await founder                           # merge == shipped

What was deleted, and why it matters

No n8n, no Oracle VM, no Cloudflare email, no Tally, no HubSpot, no GA4 API pulls, no AI API keys, no hosted client portal, no scheduler. Each removal deleted a failure class: a quota, a leaked credential, a reclaimed VM, a free-tier terms change, a vendor lock-in.

Why files, not a database

Portability (clone + passphrase restores the company), inspectability (grep beats a query), auditability (git blame on a decision), reviewability (a diff is the approval UI), and degradability: every automation has a documented manual twin in its playbook.

The only throughput ceiling

Agent session capacity, not compute minutes. Public-repo Actions are unmetered; a private repo would be capped at 2,000 minutes. Mitigation is discipline, not infrastructure: one ritual per session, batch by role, 40-minute cap, commit after every sub-step.

Why these are CI and not memory

A rule that lives in a document is obeyed on careful days and violated on the day a client is angry at 11pm. Every rule above is one that, once broken in a public repo, cannot be unbroken: history is indexed, cached, mirrored and used for model training. So the guard runs on every push and PR, on public-repo Actions, which are unmetered, and it is a plain shell script so it also runs locally before you push.

# pre-flight, before any push touching client work
$ bash os/ops/tools/public-guard.sh
✅ public-guard clean — safe for a public repo.
$ echo $?
0

The guard was itself a source of a bug worth naming: see §07. A check that errors is not a check that fails. It must fail loudly, and that behaviour is now tested, not assumed.

04 · State machines

Four machines, one rule
each: no state without a next move.

Ticket lifecycle

todoowner set→ ai-doingdraft, ugly allowed→ needs-reviewcold + critiqued→ human-doingonly Vamsi can→ donescheduled + measured blockedreason + unblock date

Hard rule: anything a client will see MUST pass through needs-review. ai-doing → done without a human is a policy violation, not a shortcut. P1 = revenue-blocking · P2 = this week · P3 = housekeeping.

Pipeline (lead)

LEAD→QUALIFIED→ DIAGNOSED→PROPOSED→ NEGOTIATING→WON→ONBOARDING ↘PARKED90d nurture ↘LOSTreason required

Transitions are only legal forward or into PARKED / LOST, and every legal move writes next_action + due. LOST without a reason is rejected by the retro ritual, because that file is how a solo agency compounds.

Client status

PROSPECT→WONadvance received→ ONBOARDINGday 0–30→DELIVERING⇄ AT_RISKamber from sentiment→ RENEWED · EXPANDED · CHURNED

No work begins on a WON with an empty 01-authority/. AT_RISK is entered mechanically (3 ambers or 1 red), not by feeling, and it is exited only by a decision recorded in the comms log.

Deliverable quality

BRIEFfalsifiable objective?→ DRAFTno self-editing→ COLD≥2h→ CRITIQUE5 rejection reasons→ FIX→GATE ≥90→SHIP

Below 75 the failure is attributed to the playbook, not the writer: R9 opens a patch in the same session. Draft and judgement in one pass is what makes AI output look like AI output; the split is the fix.

Postconditions (checked, not hoped for)

Every ritual ends with: files written at declared paths, one line in memory/log/<date>.md, a commit or PR, and the daemon-style status line ✅ R-03 · nova · 6 items · gate 93/91/90/94/92/88 · PR #12. A ritual that ends without those three is incomplete by definition.

Checkpoint discipline

Commit after each sub-step. A session interrupted at minute 3 must not lose 25 minutes of work. Because git is the persistence layer, the recovery procedure is "start a new session and read the files", which is the same recovery as a lost laptop, a dead vendor or a model change.

Idempotency

Re-running a ritual may not duplicate a deliverable, re-send an invoice or double-count a lead: writers key on slug + date + type and overwrite a version, never append a twin. Versioned names (_v02) instead of destructive edits.

Escalation format

ESCALATION · client · H/M/L then situation · what was already done · the exact rule that stopped it · A/B/C options with cost, risk, time · one-sentence recommendation · the deadline. If it takes longer than 40 seconds to answer, the escalation is the defect.

06 · Security model

The public repo is not
the trust boundary.

Design statement: this repository is world-readable by choice, so confidentiality is provided entirely by encryption at rest, and integrity of the boundary is provided by CI. "Public" is irrelevant for the vault zone; the key is everything.

# vault.sh — the sealed ledger, exactly as built
seal  1 tar -czf  .vault-work/<slug>/        # gzip first: ~5x on markdown
      2 age -z -p                     if age present   # authenticated
         else openssl enc -aes-256-cbc -pbkdf2 -iter 200000 -salt
      3 → vault/<slug>.age            # staged; git sees ciphertext
open  decrypt → .vault-work/<slug>/  # gitignored; never staged
cat   decrypt to tmpfs, print, wipe   # read one file, no plaintext on disk
key   open + re-seal every vault     # quarterly rotation
ls    name · bytes · last-changed    # health at a glance

# passphrase: $SMARTPURSUIT_KEY if set, else prompt. Never stored in a file,
# never echoed, never in a commit message, log line or chat summary.

The openssl fallback is unauthenticated AES-256-CBC: it protects confidentiality, not integrity (a public ciphertext can be tampered with, undetected). Installing age switches to authenticated encryption with no config change; the script prefers it automatically. Recommended.

Threat model · covered

Repo made public or leaked · clone of history · a laptop shared or stolen (disk has ciphertext only) · an accidental plaintext commit (CI blocks it before merge) · a competitor reading the ledger · a former contractor after offboarding.

Threat model · NOT covered

Offline passphrase guessing, if weak (the ciphertext is public forever) · the last mile: a report emailed or WhatsApped is plaintext · a compromised GitHub account without 2FA · shoulder-surfing a decrypted working copy · client-side storage after delivery · enterprise procurement requiring a named cloud and signed DPA.

Key policy (the load-bearing part)

Six or more random words, machine-generated · password manager plus one printed copy · never in the repo, the chat, or a filename · rotated with vault key each quarter and after any laptop repair or shared screen · loss is permanent: no reset, no support. Mitigation: delivered artefacts (PDF, ad account, CMS) always exist independently, so the vault is the memory, not the only copy.

Size and history math

gzip-then-encrypt keeps a 250 KB client-month around 45–60 KB. One seal per session, four sessions a week, eight clients ≈ 10–20 MB/month, under 200 MB/year, against a 1 GB comfort limit. Exports, PDFs, CSVs and screenshots never enter the tree: they are the files that eat repos.

Incident: plaintext already in history

Deleting the file is not enough. Sequence: revoke every credential the file touched → git filter-repo → force-push → rotate the vault passphrase → log the incident in the client's sealed comms file, and tell the client. Owning it in one paragraph, fast, is cheaper than being found out.

The bug that shaped this section

While auditing the repo, the guard's lead check was written as n=$(grep -c '^- id:' f || echo 0). On no match grep -c prints 0 and exits non-zero, so || echo 0 appended a second 0. The integer test then errored, the [ ] returned failure inside a subshell, and the check passed silently. A guard that can pass on error is worse than no guard, because it manufactures the confidence it exists to test.

Rewritten with grep | wc -l | tr -d '[:space:]', a digit-safety coercion, and a non-invertible rule: any real lead id in the public tree fails, whether or not a vault exists. Then tested in four states, not two: clean ⇒ 0 · one record ⇒ 1 · record with a vault present ⇒ still 1 · restored ⇒ 0. Two further false positives were found by the same sweep (a documented schema example counted as a record), so the detector now matches the id shape, not the word.

Engineering rules for any job added here

Idempotent: re-run must not duplicate a deliverable or double-send 1
Never destructive: write new versions, never overwrite client data 2
Quota-aware: read stack/limits.yml, park at 80%, never retry a 429 3
No external sends: everything client-facing lands in 10-outbox 4
Fail loud in one line, and never on a shell error 5
Linux runner only · under 2 min · concurrency group · small reviewable diff 6
Every job must have a documented manual twin in its playbook 7

Rule 7 is what makes the whole "no servers" architecture acceptable: a dead job degrades to a written routine, never to silence. If a job cannot be described in a playbook, it is not a job, it is a hack.

08 · The gate as a function

score(out) → 0…100
ship only when ≥90.

The rubric is the load-bearing part of the whole design: it is the only reason one senior person can be trusted with team-level pricing. So it is specified as a function with hard failures, not as advice.

def gate(deliverable, client):
    score  = 25 * truth(deliverable)        # every number resolves to a
                                           # dated source in 04-analytics
    score += 20 * (not generic(deliverable))  # a competitor could send it?
    score += 15 * fit(client, ref_count=3)   # ≥3 facts from 00-account
    score += 20 * actionable(owner=True, date=True)
    score += 10 * craft(deliverable)         # format, tone, export specs
    score += 10 * honest(assumptions, failure_modes)

    score -= 5 * banned_vocabulary(deliverable)   # unlock · elevate · seamless…
    score -= 25 * unsourced_numbers               # hard fail at any total
    score -= 15 * broken_paths_or_links

    if scope_exceeds(sow): return FAIL("change request first")
    if score < 75: raise PlaybookDefect(playbook)   # patch the process
    return SHIP if score >= 90 else REVISE(once)

# the critique step is a separate role, never the writer's mood:
# "You are a hostile reviewer paid to find 5 reasons a CFO rejects this."
# output is a numbered list of weaknesses — not a rewrite.

Per-type required checks

Content: intent answered in the first 100 words · entities covered · 3+ internal links · meta within limits · no cannibalisation against the index · CTA specific · no padding to reach the band. Paid: naming convention · conversion verified by test, not configuration · budgets sum to the cap · negatives loaded · a stop rule per ad set · placement specs. Report: baseline column · three-sentence summary · anomaly with a hypothesis · one ask · no chart without interpretation · dates on every figure.

Storage

The score is written into the ticket's frontmatter (score:) and into the PR description as a per-item line, so the merge commit itself becomes the audit record. A2 exists to fail the build when a merged deliverable has no score.

Why 90 and not 100

A perfect score is either unattainable or being faked, and a threshold nobody meets on the first pass becomes a ritual that gets skipped. 90 with hard failures keeps judgement with the human while making the cheap, embarrassing errors structurally impossible.

The founder's three questions (30 seconds)

Would I put my name on this in front of this owner · is there a number in here I cannot trace · what will the client do after reading it. Failing any: back it goes. Never "fixed live" in the send box.

12 · Test plan

Nothing in this system
is "assumed to work".

There is no test suite, because there is no application. What exists instead is a short list of adversarial checks, each of which has already caught something real. Run them after any change to a script, a schema or a workflow.

T1 · GUARD

Four states, not two

Clean tree, one real lead, one lead with a vault present, restored — each must produce the expected exit code with nothing but its own message on stderr. Every rule added since gets the same treatment: plant it, expect 1, remove it, expect 0.

CAUGHT: the silent-pass integer bug · a schema example miscounted as a record · a finance doc that documented a public ledger path with a client name in it
T2 · VAULT

Leak and round-trip

Plant phone, GSTIN, PAN and card digits inside a client folder, seal, commit, then search the entire history for the plaintext. Open, edit, re-seal, verify byte-identical restore, and confirm a wrong key exits 1 rather than producing garbage.

CAUGHT: verified no plaintext in history · verified size compression before encrypting
T3 · SCHEMA

Everything must parse

All YAML through a real parser, and a scan for markdown fences inside data files. Then resolve every backticked path in every markdown file against the tree.

CAUGHT: 3 unparseable configs · 5 dangling references · 2 indexes posing as listings
T4 · ARITHMETIC

Every number must add up to what we claim

Scoring weights total 100 before the capped bonus; the gate's six rubric weights total 100; every published rupee figure on the site must equal SOVEREIGN.md and RATES.md; folder numbers must be unique.

CAUGHT: lead weights summed to 105 · the gate summed to 95 against a stated 100 · the site still published the pre-revision ₹10L floor · two folders both claimed number 13
T5 · SURFACE

Pages render and print

Tag balance, JS syntax check, HTTP 200 on every asset, and a print render for the client-facing PDF path. A page whose reveal script errors must never leave content invisible.

CAUGHT: a broken selector from a batch edit · shared reveal.js replaced four duplicated inline blocks
T6 · RED TEAM

The week 12 gate

Run five hostile requests through the OS: a fake-review demand, a billing dispute, a "guarantee page 1" request, a scope bully, and a leaked-credential email. The pass condition is not polite answers, it is that each one ends as a rule in a file.
